# 记忆回溯：项目现状与后续路线

> 最后更新：2026-08-10
>
> 适用分支：`prototype`
>
> 作用：跨设备、跨 Agent 的项目交接事实来源。开始工作前必须完整阅读。

## 一、产品目的

记忆回溯是一个围绕**地点与人生记忆**构建的私人记忆产品。它不是普通相册、日记、
知识库或社交产品。核心体验只有一件事：

> 让一个人通过地点、照片和文字，重新进入自己过去的人生。

产品最终包含两个正式客户端：

- React Native 手机 App：负责快速采集照片、文字、时间和地点，并支持离线保存。
- React 电脑 Web：负责在大地图上按照世界、国家、城市、地点逐层回溯记忆。

所有记忆默认且强制为私人内容。照片、正文、标题、标签、地点和经纬度必须先在用户
设备上加密，再上传服务器。服务器可以保存账号与同步所需的普通元数据，但不能读取
用户的私人记忆内容。

首版不做社交、公开主页、用户分享、AI 照片分析、未来信件或软木板等扩展功能。

## 二、仓库位置与边界

- 当前代码位于 ThinkPad 仓库的 `prototype` 分支：
  `memory-recall-mobile/`。
- 它不读取 ThinkPad 数据，也没有接入原有 Supabase、Cloudflare 或 Camp Memories。
- 当前仍与 ThinkPad 共用 Git 仓库；在 Web 正式开发前，计划拆为独立
  `memory-recall` 仓库。
- 当前 UI 只是加密和真机测试壳，不代表正式产品界面。

## 三、当前已经完成

### 1. Android 加密核心

- Expo SDK 57、React Native Android 原型已经建立。
- 私密空间密码通过 Argon2id 派生解锁钥匙：64 MiB、3 次迭代、并行度 1。
- 解锁钥匙保护 VMK；VMK 再保护一把文字钥匙和一把照片钥匙。
- 文字和照片使用 AES-256-GCM，每次加密使用随机 IV。
- AAD 将密文与用途、记录 ID、记录版本或照片类型绑定。
- VMK 不以明文写入磁盘或 SecureStore。

### 2. 本地密文存储

- 一条测试记忆被整体序列化为 JSON 后加密。
- SQLite 不保存记忆或照片明文。
- 照片原始字节完整加密后保存为 `.bin` 文件。
- SQLite 只保存解密所需的密文、IV、ID、类型、版本和密文文件路径等信息。
- 解锁后才在内存中构建文字对象或照片预览。

### 3. 密码与设备解锁

- 支持私密空间密码解锁和错误密码拒绝。
- Android Keystore/SecureStore 保存随机设备钥匙。
- 设备钥匙通过系统生物识别保护，并用于解开 VMK，不保存用户密码。
- 支持手动锁定并清零可控的 `Uint8Array` 钥匙。

需要准确描述：JavaScript 字符串、已经解密的对象和 Base64 预览由运行时垃圾回收管理，
无法承诺物理内存立即完全擦除。

### 4. 加密备份与换机恢复

当前可以导出一个完整的加密 JSON 包，内容包括：

```text
加密 JSON 包
├── vault：密码保护后的 VMK、文字钥匙和照片钥匙
├── memories[]：记忆密文
└── photos[]
    ├── 加密后的照片元数据
    ├── IV 等协议参数
    └── 照片密文的 Base64 数据
```

JSON 包包含图片数据，但包含的是加密后的照片密文，不是可打开的 JPG/PNG。恢复时选择
JSON，写回 vault、记忆密文和照片 `.bin`，再输入原私密空间密码解锁。

### 5. 已完成验证

截至 2026-08-10，用户已在 Android 真机确认以下五项全部通过：

1. 原生 Argon2id、AES-GCM 与网页固定向量兼容。
2. 正确密码可解锁，错误密码不能解锁。
3. 真实照片可以加密、保存、解密和预览。
4. Android 指纹/生物识别可以解锁设备上的私密空间。
5. 导出、清空本机、导入并使用原密码可以恢复文字和照片。

仓库现有 TypeScript 类型检查通过，自动协议测试 6/6 通过。本机也已成功生成 Android
release APK。

## 四、已经拍板的决定

除非用户明确改变决定，后续 Agent 必须遵守以下内容。

### 1. V1 共用一把照片钥匙

V1 采用：

```text
私密空间密码
└── VMK
    ├── textKey
    └── photoKey（所有照片共用）
```

不改为每张照片独立生成和包装一把钥匙。每张照片仍必须使用独立随机 IV，并通过 AAD
绑定照片 ID、类型和数据部分。不要为了理论上的扩展能力提前增加密钥层级。

### 2. 同步只做最小闭环

服务器阶段只需让用户看懂一条记忆是否安全到达云端。最小状态为：

```text
仅本地 → 正在加密 → 等待上传 → 上传中 → 已同步 / 同步失败
```

这些状态应在真正对接服务器时实现。当前数据模型阶段不提前建设复杂任务调度、工作流
引擎或通用同步框架。

### 3. 服务器不得知道私人记忆内容

Memory 的标题、正文、标签、位置、经纬度、时间相关私人信息和照片元数据需要作为一条
JSON 在设备端整体加密。服务器只能获得同步必要的 ID、版本、数量、大小、时间和状态等
普通元数据。

当前测试用 Memory 只有：

```ts
{
  id,
  title,
  body,
  date,
  createdAt,
  photoId?
}
```

它不是正式产品模型；目前一条记忆最多关联一张照片。密文外层的 `version` 是记录修订号，
不是计划中的 `schemaVersion`。

## 六、当前备份方案的容量边界

当前 JSON 包会把所有照片密文转换为 Base64，并一次性读取、生成或解析整个文件。
Base64 通常使数据体积增加约三分之一。100 张、平均每张 10 MB 的照片会产生约 1.33 GB
的 JSON，手机运行时内存占用还会更高，因此当前实现不能保证稳定恢复 100 张以上的原图。

当前方案只用于加密闭环和换机恢复原型验证。正式备份应改为：

```text
备份容器
├── 小型 JSON 清单
├── memory 密文
└── 多个独立照片 .bin 密文
```

导出和恢复逐项处理，避免一次性把所有照片装进内存。导入时先完整校验并写入临时区域，
全部成功后再替换旧数据。这个改变只影响备份容器和读写方式，不改变共用 `photoKey` 的
决定，也不需要现在提前实现。

另一个当前限制是：导入函数会先清空现有本机密文，再逐项写入备份。如果包损坏或写入
中断，可能失去原有本机数据。正式版本必须改为校验成功后原子替换。

## 七、下一步路线

严格按照以下顺序推进，每一步都只实现可验收的最小范围。

### 第一步：正式 Memory V1

不依赖云资源，完成：

```ts
{
  id,
  title,
  text,
  date,
  tags,
  location: { name, city, country, lat, lng },
  photos,
  createdAt,
  updatedAt
}
```

- 整条 JSON 使用 `textKey` 加密。
- 建立 `cryptoVersion` 与 `schemaVersion` 双版本。
- 增加旧结构到正式结构的迁移机制。
- 增加固定向量、结构校验和版本迁移测试。
- 只为未来同步保留必要字段，不提前实现服务器或复杂队列。

### 第二步：服务器最小闭环

- TypeScript/Fastify API。
- 手机验证码登录。
- PostgreSQL 保存用户、设备、密文记录和同步元数据。
- 私有腾讯云 COS 只保存加密 `.bin` 文件。
- App 将现有本地流程接到最小上传队列。
- 验收一条文字、一处地点和一张照片经过服务器后可在另一设备恢复。

### 第三步：Web 回溯体验

- React Web 使用与移动端相同的协议和固定向量。
- 世界 → 国家 → 城市 → 地点 → 记忆逐层进入。
- 地图始终保留为背景，打开记忆时在地图上展开照片和文字。
- 地区树由浏览器解密后在本地构建，服务器不知道用户去过哪里。
- 地图与搜索统一使用高德；搜索通过自有 API 代理且不保存搜索词。
